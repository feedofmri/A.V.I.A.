# A.V.I.A. code and implementation audit

Audit date: 12 November 2026, user timezone Asia/Dhaka. Reviewed revision: `190c91ca791faf4712e976b7cd673275bdbb23f8` plus the running local deployment.

The application has a working local telemetry-to-inference-to-dashboard path. It is suitable for demonstrating the supplied model artifacts and UI concepts. It needs substantial reliability, access-control, and ML reproducibility work before it can be treated as a dependable crew monitoring system. Passing integration tests establish that the software connects and produces expected example outputs; they do not establish predictive accuracy or medical validity.

Application source was not changed in this audit. Reports and diagnostic scripts were added. Write-heavy defect probes ran against a disposable copy of the demo database on a separate API at port 3300. That API container and database were removed afterward. Existing repository end-to-end tests ran against the normal demo stack and restore the logical values they change, while adding telemetry history as part of their normal behavior.

## Scope and evidence

Reviewed the React clients, BFF, core API, SQL migrations and RLS, inference API, adapters and fusion pipeline, supplied model artifacts, Docker setup, tests, architecture notes, three integration DOCX files, original project-plan PDF, and frontend design spec. Compared current implementation with the newer integration docs separately from features proposed in the original plan.

Limits: no browser-driven visual/accessibility test suite, real wearable/BLE test, disconnected-device field trial, full Python/container vulnerability scan, sustained load test, independent training-data verification, clinical assessment, or held-out accuracy study was performed. Source review identifies UI behavior; it does not certify every rendered viewport. Findings below distinguish reproduced defects from source-confirmed gaps and risks.

Keep this stack for the next iteration. A framework rewrite would not address the verified problems. Prefer a shared contract package, reliable ingestion semantics, and an explicit distinction between observations, model outputs, heuristics, and demonstrations.

## Findings requiring priority fixes

P1 means fix before shared deployment or presenting the affected behavior as dependable monitoring. P2 means fix for a reliable pilot or feature-complete demonstration. P3 means maintenance and operational improvement. Priorities reflect this project's context, not a formal vulnerability score.

### F01 P1 Unauthenticated callers can read and change every crew scope

**Evidence:** `server/src/app.ts:10`, `server/src/routes/crew.ts:47`, `server/src/services/crew.ts:34`, `bff/src/app.ts:11`, and `docker-compose.yml:16`. Requests without credentials to crew state, another crew member's baseline, and mission returned 200. Write handlers also have no identity/authorization checks. Compose publishes DB, Redis, core, BFF, and inference ports on all host interfaces by default; Redis has no configured authentication and DB has documented development credentials.

**Impact:** RLS prevents accidental cross-scope SQL access, but it does not authorize which crew a caller may select. The BFF can be bypassed through published core and inference ports. CORS does not supply authentication.

**Fix:** Add locally verifiable identities and crew/operator roles; authorize each resource and administrative action; derive crew scope from identity. Keep internal services on the Docker network and bind necessary development ports to loopback. Configure secrets and transport protection for shared use. Test requests from multiple identities, not only different URL IDs.

### F02 P1 Critical alerts can produce a Warning crew badge

**Reproduced:** A nominal Brandt payload with `spo2_pct: 80` returned a Critical hypoxia alert but `crew_status_badge: Warning`. The anomaly score remained 0.1026, identical to SpO2 98. `agent/src/engine/pipeline.py:220` only promotes a Nominal anomaly tier to Warning when any alert exists. The cardiac adapter accepts SpO2 for output/quality checking but does not put it in the learned feature vector (`model files/cardiac_encoder.py:70`).

**Related:** `pipeline.py:421` maps every non-Nominal skeletal region to top-level Warning, including a Critical region.

**Fix:** Define a single severity aggregation rule using the highest active severity across validated guardrails and model outputs. Clearly distinguish rule detection from learned-model sensitivity. Test severe oxygen inputs, multiple simultaneous alerts, and critical skeletal regions. This finding concerns internal status consistency, not validation of the chosen medical thresholds.

### F03 P1 Backfilled telemetry can resolve current alerts

**Reproduced:** The disposable database had active Diaz stress/cardiac alerts. Ingesting a normal reading timestamped one hour earlier removed both alerts while the latest vital ID and Warning status stayed unchanged.

**Evidence:** `server/src/services/telemetry.ts:268`, `:183`, `:342`. Every inference synchronizes the live alert set, regardless of its event timestamp. Older results can overwrite `last_seen_at` or resolve newer conditions.

**Fix:** Separate historical inference storage from current-state/alert evaluation. Use event-time watermarks and a transaction-scoped per-crew ordering strategy. Older events should enrich history without mutating the live alert state unless an explicit replay rebuilds that state in order. Test delayed uploads, equal timestamps, and concurrently completing requests.

### F04 P1 Offline-first behavior is incomplete and failed delivery can lose information

**Source-confirmed:** Pulse stores crew data in React memory (`client-pulse/src/App.tsx:17`, `src/lib/store.ts`). Symptoms update local state and swallow upload failures (`App.tsx:86`); tasks are local only (`:93`). There is no IndexedDB outbox, service worker/app-shell cache, reconnect replay, or device sequence protocol. Initial state includes nominal values and synthetic HR history. A failed telemetry submission still sets `syncedAt` to the current time (`:125`).

**Impact:** Reloading can lose unsent symptoms/tasks, initial defaults can resemble observations, and a fresh sync time can be shown for a failed attempt. Running inference on a local server permits operation without internet after installation, but does not make a disconnected Pulse device reliable.

**Fix:** Durable local outbox, explicit pending/sent/failed states, server acknowledgments, idempotent replay, reconnect recovery, and an installed/offline app shell. Display unobserved initial values as unknown. Keep submission-attempt time separate from last server acknowledgment.

### F05 P1 Stale model results and fabricated twin values can appear current

**Reproduced:** The legacy raw-vitals endpoint accepted `{}` as a new reading. Crew state then returned `inference_current: false`, null HR, and the prior Warning badge. `server/src/services/telemetry.ts:447` computes freshness but still returns the old badge, scores, and forecast. The BFF exposes `inferenceCurrent`; the Cockpit `CrewMember` type and rendering do not use it. Freshness also compares record IDs, not elapsed time or baseline version.

**Source-confirmed:** Digital Twin catches a backend failure, sets `twin` to null, and silently restores static `LAYERS` values (`DigitalTwin.tsx:324`, `:415`). Most anatomy metrics remain constants even when the backend succeeds. The view does not refetch when new crew telemetry arrives unless crew selection/adherence changes.

**Fix:** Model age, measurement age, baseline version, unknown/degraded states, and explicit provenance labels. Do not replace unavailable telemetry with unlabeled plausible numbers. Disable predictions/actions that depend on missing data. Require at least one observation for raw input, or remove the legacy route. Test backend loss after a successful load and an expired model result.

### F06 P1 Fusion model equivalence and predictive validity cannot be established from this repository

**Evidence:** `agent/src/engine/fusion.py:1` explicitly reconstructs missing model classes from tensor names/shapes and documentation. Parameter-free activation, residual, and gate behavior are selected using three reference cases. `strict=True` confirms compatible parameter names/shapes, not the original forward computation. The repo contains no training notebooks, original fusion export, split manifests, or held-out reports.

**Fix:** Obtain the original trained architecture and preprocessing/export pipeline, plus golden inputs/outputs generated by its author. Ship an immutable model bundle with checksums, architecture configuration, scaler state, feature order, dataset provenance, training/evaluation metadata, and a model card. Validate equivalence before evaluating accuracy. Do not tune against the same examples used to claim validation.

## Further implementation defects and gaps

### F07 P2 Telemetry lacks idempotency and deterministic tie-breaking

**Reproduced:** Posting an identical payload twice with the same timestamp created vital IDs 900 and 901 in the audit database. Both API responses reported ID 900 because the response reads current state using only `ORDER BY recorded_at DESC`.

**Evidence:** `telemetry.ts:316`, `:437`, `:440`; schema has no device-event identity. Equal timestamp rows can select different latest vital/inference records, so freshness can also be wrong.

**Fix:** A unique device/event identifier or idempotency key; stable ordering such as event time plus sequence/ID; return the actual committed event identity independently of current-state identity. Test retries after a timeout and duplicate/out-of-order delivery together.

### F08 P2 Countermeasures collide across crew members

**Reproduced:** The same label assigned to Brandt and Sato returned the same row ID. The second response claimed Sato, but a subsequent list showed the row assigned to Brandt.

**Evidence:** `server/migrations/002_avia_domain.sql:122` has `UNIQUE (scheduled_for, label)`; `server/src/services/insights.ts:85` only updates its timestamp on conflict, then constructs response crew_id from the requested crew.

**Fix:** Uniqueness must reflect the intended schedule/crew/plan identity, including explicit handling for mission-wide items. Return persisted values. Test two crew members receiving identical activities on the same day.

### F09 P2 Analytics warning direction is wrong for three vitals

**Evidence:** `AnalyticsView.tsx:154` marks every value above `warnLine` as warning. That reverses the intended direction for SpO2, HRV, and sleep; normal high values can appear amber while low values do not. Chart thresholds also differ from backend alert rules, and all vital cards use a nominal tile class.

**Fix:** Shared rule metadata with unit, direction, and range; use the same policy version on both sides. Explicitly label general chart guides when they differ from personal-baseline alerts. Add UI checks for low SpO2/HRV/sleep and high HR/EDA.

### F10 P2 Chart time axis and forecast meaning are misleading

**Evidence:** `server/src/services/insights.ts:113` truncates history to 17 hourly, 7 daily, or 23 daily buckets to make room for seven forecast bars. The client labels indexes as hours/days (`AnalyticsView.tsx:198`) instead of using returned historical timestamps. Forecast values are the same seven model steps for every display range; the trained context is described as 12-hour steps, but future timestamps/step duration are not in the chart contract.

**Fix:** Timestamp all historical and future points; preserve missing buckets; show the actual horizon and cutoff; use one consistent temporal scale or clearly separate the panels. Do not change model horizon just by changing chart range.

### F11 P2 Forecasts, confidence, and data quality need precise provenance

**Evidence:** `pipeline.py:292` extrapolates the fused embedding slope and reruns score heads. `:305` maps changing score deviations to vital forecasts with a handwritten formula; there is no trained vital-regression head or prediction interval. Confidence is an average of distance from 0.5 and stage confidence, multiplied by the fraction of valid modalities (`:210`). It is not measured prediction accuracy. A cold-start input with five padded history steps still reported 100% quality in the probes.

Suit zone classification uses neural weights, but swelling percentage is an impedance arithmetic formula, body-map tiers are threshold rules, and `depressurization_prob` is `1 - P(nominal class)` (`model files/suit_swelling_encoder.py:93`, `:137`). Bone projections are explicitly a heuristic bridge, and NASA context is a reference-vector construction, not another trained neural encoder.

**Fix:** Return method/provenance per output. Label forecasts as experimental extrapolation until evaluated against future observations. Separate data completeness, measurement quality, model uncertainty, and calibrated confidence. Preserve signed Shapley values: current percentages normalize absolute effects on the anomaly head and are not causal contributions or explanations of each distinct alert/head.

### F12 P2 Invalid or missing context silently becomes a different reference context

**Reproduced:** `mission_timepoint: R+999` returned 200 and used R+1. `crew_code: C999` returned 200 using population-average CBC context. `pipeline.py:73`, `agent/src/api/schemas.py`, and `model files/nasa_context_encoder.py:62` allow these fallbacks. Every integer mission day maps to R+1; demo crew codes point to supplied reference subjects rather than newly measured astronaut CBC data.

**Fix:** Validate known timepoints and subject identifiers, explicitly label population/reference fallback, and flag missing context. Add actual mission-subject mapping and a versioned measurement source if supporting new crew. Avoid presenting reference subjects' blood shifts as current crew measurements.

### F13 P2 Masked sleep input still generates a sleep health alert

**Reproduced:** A nominal reading with EOG 200 returned `Sleep` mask 0 and quality 75%, yet generated a sleep warning from that encoder's output. Fusion masking does not prevent `_alerts` from using invalid modality outputs (`pipeline.py:159`, `:333`).

**Fix:** Pass modality quality into alert generation. Distinguish sensor/data-quality alerts from physiological alerts; define validated fallback behavior. Test each missing/bad modality and ensure the UI shows untracked data.

### F14 P2 Mission-day validation disagrees across layers

**Reproduced:** Mission setup accepted day 301. After a raw reading with no carried mission day, otherwise valid telemetry returned HTTP 500 because `vitals.mission_day` permits only 1–300. Existing readings can mask this because completion carries the previous mission day forward, rather than using the newly configured mission day.

**Evidence:** `server/src/routes/mission.ts:23`, `telemetry.ts:140`, `server/migrations/002_avia_domain.sql:60`. Numeric strings in telemetry also have weaker bounds than integer values. BMD baseline endpoint accepts exact 0.3 and 2.0 while the inference TwinRequest excludes both endpoints.

**Fix:** Shared validated schemas and consistent boundary semantics. Decide whether phase belongs to the event or current mission configuration. Return actionable 422 errors before writing. Cover 0/1/300/301/1000, numeric strings, unsupported phases, and BMD boundary values.

### F15 P2 Advertised acknowledgment and task synchronization are incomplete

**Evidence:** Core/BFF expose alert-state PATCH routes, but Cockpit has no API client method or acknowledgment controls in `AlertsView.tsx`. Pulse subscribes to ack messages, but Cockpit never publishes them. Pulse tasks are a static local list; no task API hydration/write path is used. The dev-only `/__avia` relay is not a production transport and Cockpit does not subscribe to it. Twin success copy claims delivery via encrypted BLE (`DigitalTwin.tsx:1224`) without a BLE implementation.

The twin push-state key also omits crew ID (`:529`), so sending one crew's plan can disable the button for the next crew in the same part/layer.

**Fix:** Implement server-backed task plans, acknowledgment actions/history, delivery receipts, and reconnect sync; include crew identity in UI keys. Until implemented, remove unsupported delivery claims and label simulations. BLE is optional if a secured local Wi-Fi protocol fulfills the selected product scope.

### F16 P2 Suit results do not drive the 3D body map

**Evidence:** `SuitIntegrityPanel.tsx:110` owns results locally and renders a zone banner/table. It does not pass `digital_twin_body_map` into DigitalTwin's `partsState` or `AviaTwinController`. The integration DOCX specifically asks that result to recolor body meshes.

**Fix:** Lift suit result state to the twin, map regions to meshes, and define the precedence between physiological and suit overlays. Test left/right/legs/torso scenarios and remove stale results when changing crew. Classifier results and the rule-based region map should retain separate labels.

### F17 P2 Missing inference is stored but has no recovery workflow

**Evidence:** `telemetry.ts:356` can return 503 with `vital_persisted: true`, but no worker, pending-inference status table, retry/backfill job, or client reconciliation exists. The frontend error types discard structured persistence information. Retrying manually creates another reading. A later twin-call failure can coexist with an already computed inference, further complicating the 503 meaning.

**Fix:** Explicit ingestion state such as accepted/pending/scored/failed, durable work scheduling, bounded retry, and idempotent reconciliation. Preserve recorded events even when inference is unavailable; surface that state separately from submission failure. Test outage/restart and partial pipeline failure.

### F18 P2 Preprocessing and temporal completeness are not reproducible enough

**Evidence:** Adapters fit RobustScaler on deployment CSVs at startup instead of loading a frozen training scaler. Inference substitutes medians or synthesizes waveform features from scalar UI values. Core carries EEG values indefinitely without age limits; changed sleep duration can retain old EEG. `historySteps` omits missing 12-hour slots and the agent pads only at the beginning, compressing internal gaps instead of representing their actual positions.

**Fix:** Export training preprocessing with the model; validate feature schema/checksums and units. Store source, age, uncertainty, and imputation method per measurement. Preserve fixed time slots with masks/time deltas. Add held-out evaluations for manual-feature approximation and missing-history behavior. Fitting on an entire evaluation dataset would be leakage; this audit could not establish the original train/evaluation split.

### F19 P2 Baseline edits do not invalidate prior model semantics

**Evidence:** `server/src/services/crew.ts:76` updates baseline values; BFF clears cached views, but previous inference outputs and alerts remain computed from the old baseline. `inference_current` checks vital ID only, so the old model result can still be marked current. Mission setup performs baseline and mission writes independently; a second-write failure leaves the first applied.

**Fix:** Version baselines and policy/configuration, persist those versions with every inference, and define when to recompute current state. Make multi-resource save behavior transactional or explicitly report partial success. Guard selection changes against stale form-load responses in `MissionSetupView`.

### F20 P2 Offline deployment still requests Google Fonts

**Evidence:** `client-cockpit/index.html:7` and `src/styles/global.css:6` load Google Fonts. Both the frontend spec and integration spec require local fonts/zero external runtime requests.

**Fix:** Bundle licensed font files or use system fonts; test an installed production build with network access disabled and inspect all requests. Separately distribute prebuilt container images and all model dependencies for installation in a disconnected environment.

### F21 P2 Development dependencies have known advisories

**Measured:** Cockpit has 8 npm package findings, including one high; Pulse has 2, including one high. Vite 5 and esbuild are involved; Cockpit also has shadcn/transitive tooling findings. These counts are dependency-tree findings, not ten distinct exploitable production vulnerabilities. Both frontend `--omit=dev` scans returned zero, and nginx serves static production output. Development servers remain affected attack surfaces.

**Fix:** Update through a reviewed compatibility plan, remove unused tooling, and rerun builds and advisories. Do not run `npm audit fix --force` blindly: the suggested changes include major upgrades and a shadcn version downgrade. The audit did not assess Python package or base-image CVEs.

### F22 P2 Outages can hang or mislead readiness and polling

**Evidence:** `bff/src/clients/api.ts:19` performs fetch without a deadline. Client requests also lack deadlines/cancellation. Cockpit polls with setInterval without preventing overlapping refreshes; a slow earlier response can replace a newer result. Redis invalidation can race with an in-flight cache fill. Core health waits for ML health with a 10-second timeout while Compose healthcheck allows only three seconds, which caused unhealthy startup behavior while the inference service was absent.

**Fix:** Bounded request deadlines, cancellation, single-flight polling or sequence checks, cache versioning, and separate inexpensive liveness/readiness/capability checks. Add explicit degraded-state banners on every view, not only an empty initial overview. Validate controlled backend/cache/inference outages.

### F23 P2 Twin view leaks window event listeners on remount

**Evidence:** `AviaTwinModel.ts:686` installs pointermove/pointerup listeners; `destroy():789` never removes them. Renderer disposal also does not traverse and dispose all scene geometry/material resources. Repeatedly entering/leaving the view retains controller closures and can retain graphics resources.

**Fix:** Keep listener references or an AbortController for cleanup; dispose owned scene resources and tooltips. Test repeated mount/unmount cycles and track listeners/GPU memory.

### F24 P2 Some apparently complete product features are placeholders

**Evidence:** Behavioral Health has a fixed sentiment curve, fixed Isolation count, and Voice/Text buttons without handlers. It is labeled not model-derived, which is helpful, but the journal privacy copy describes a workflow that has not been built. Twin non-BMD metrics and prescribed countermeasure text are static, including medication/exercise instructions; there is no author/reviewer/version/approval model. `ml/README.md` describes LSTM/NLP/export work that is not present.

**Fix:** Either mark these controls unavailable/demo with precise explanations or implement scoped functionality. Prioritize a documented, reviewable countermeasure library and execution tracking before expanding automated recommendations. Treat journal storage/consent/encryption as a distinct feature; NLP and local learning are optional later research, not prerequisites for repairing the telemetry product.

## ML assessment

The supplied cardiac, stress, sleep, suit, and fusion weights load and execute. The NASA context module computes reference features from CSV data. The registry checks required artifacts, loads expected weights, uses evaluation mode, repairs known missing CBC indices, and reports model availability. These are useful implementation strengths.

The main scientific limitation is evidence. Reference-case tests verify integration and selected outputs; forecast tests primarily verify shape and length. The suit documentation's classification of all training rows is a training-fit check, not held-out accuracy. No training/evaluation artifacts in this repository substantiate sensitivity, specificity, calibration, false-alarm rate, forecast error, or generalization to astronauts, devices, or future missions. Cross-subject validation claims in handoff documents cannot be independently reproduced here.

Required evaluation package:

1. Original model definitions and frozen preprocessing with numerical parity fixtures.
2. Dataset IDs/licenses, subject/session split manifests, feature provenance, exclusions, and artifact checksums.
3. Subject-separated and time-separated evaluation, with preprocessing learned only on training data.
4. Per-task discrimination metrics and calibration; confidence reliability curves rather than raw output certainty.
5. Forecast backtesting against actual future measurements at declared horizons, compared with last-value and baseline predictors.
6. Missing/noisy/stale sensor, cold-start, extreme-value, context-fallback, and device-shift evaluations.
7. Latency distributions and resource measurements on intended hardware, including concurrent inputs and explanation costs.
8. Versioned decision rules and traceable human review for any operational recommendation.

No stronger clinical or predictive claim is supported by the current audit.

## Additional operational and maintainability work

- Add CI for all four builds, server/ML tests, isolated integration tests, formatting/type checks, dependency scanning, and model-bundle parity checks. No CI workflow or frontend/BFF-specific test suite was found.
- Add browser tests for telemetry entry, alert severity, acknowledgment, crew switching, failed requests, chart semantics, suit overlays, and responsive layouts. Add keyboard/focus tests: alert rows are click-only divs, and modal/drawer focus containment/restoration is incomplete.
- Add startup/configuration validation, graceful SIGTERM/SIGINT shutdown, DB connection/query timeouts, and resource budgets. Node `onClose` cleanup exists, but index files do not register signal handlers to invoke it.
- Separate liveness, readiness, model capabilities, seed completion, and data freshness. Make startup visibly report which phase is incomplete.
- Make seeding resumable after partial failure: it currently skips a crew if any seeded telemetry exists, so an interrupted seed can leave incomplete history permanently skipped on rerun.
- Add structured operational metrics for ingest failures, pending inference, duplicate events, event lag, alert transitions, inference latency, cache errors, and last successful device contact.
- Add backup/restore verification, retention/export, deletion policies, migration checksums, and an offline release manifest. SQL migrations already use transactions and an advisory lock, which should be retained.
- Keep audit history for alert acknowledgments, baseline edits, mission changes, and countermeasure plans. Current records generally store the latest state without an actor/change history.
- Split the 732.67 kB Cockpit JS bundle; load the twin and heavyweight features on demand. Inspect/remove unused Fiber/drei and development tooling. Reduce the large monolithic twin component and layered CSS overrides without changing behavior.
- Consolidate repeated TypeScript/Pydantic/JSON-schema contracts through generated schemas and versioned API responses. Include event identity, observation time, model/policy/baseline version, provenance, and freshness in each state.
- Document a single mission clock and calendar policy. Alert times use UTC while Pulse formats local time and DB schedules use its current_date; avoid comparing unlabeled time-only strings across dates/devices.
- Record code/data/model licenses and consent constraints before distributing the project and training artifacts. No top-level license/model card was found in the reviewed tree.

## Recommended implementation sequence

### Stage 1 Make the current demonstration truthful and consistent

Fix Critical severity propagation, backdated alert mutation, countermeasure uniqueness, duplicate/timestamp semantics, chart warning directions, mission bounds, masked-modality alerts, and stale-result rendering. Label all heuristic/static outputs. Remove unsupported BLE/sync claims and nonfunctional controls. Bundle fonts. Upgrade affected development dependencies through tested changes.

Acceptance: every reproduced defect has a regression test; no current screen presents historical/static values as fresh observations; model and rule outputs have clear provenance.

### Stage 2 Complete reliable local operation

Add identities/roles, internal service isolation, durable Pulse outbox, idempotent ingestion, pending inference/replay, server-backed tasks and alert acknowledgment, versioned configuration, and delivery receipts. Connect suit output to the body map. Add browser and outage tests plus backups and observability.

Acceptance: restart/disconnect/reconnect loses no accepted events; stale or pending processing is visible; permissions work across identities; tasks and acknowledgment converge across devices.

### Stage 3 Establish reproducible ML evidence

Obtain original fusion code and preprocessing exports, implement model manifests/parity tests, evaluate on independent subjects/time periods, calibrate outputs, and backtest forecasts. Freeze a model release before benchmarking on intended hardware.

Acceptance: anyone with the permitted datasets and release artifacts can reproduce the declared evaluation and model outputs. Experimental heuristics remain explicitly identified.

### Stage 4 Add features supported by an actual mission need

Prioritize device adapters, timeline review/export, explainable alert history, schedule adherence, maintenance tools, and optional secure local journals. Add BLE, edge model export, NLP, or local training only after selecting hardware, datasets, privacy requirements, and measurable success criteria. Broad new AI features should not delay fixes to existing monitoring behavior.
